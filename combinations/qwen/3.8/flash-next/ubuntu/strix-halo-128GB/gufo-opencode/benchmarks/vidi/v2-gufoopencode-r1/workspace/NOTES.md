# Notes

Decisions and deviations made while implementing stories 1 and 2.

## Story 2 (sticky notes)

- **`createSticky` returns `string | false`.** The design implies it returns the new note id, but the spec requires double-click on a non-finite coordinate to be a no-op, so `createSticky` returns `false` (rather than throwing) when a coordinate is not finite and only creates a note when all inputs are finite (TC-39). Callers treat a falsy return as "nothing was created".
- **Toolbar lives inside `BoardViewport`, not `App.tsx`.** For the same reason as story 1 (the camera is owned by `BoardViewport` and the "Sticky note" button must drop a note at the world point under the screen centre), `BoardViewport` renders the story-2 `Toolbar` and the `StickyNote` children inside the world layer. `App.tsx` wires `useBoardDoc`, `useSelection`, `useNoteKeys` and mounts `BoardViewport`.
- **Selection is local UI state.** Selection is deliberately kept out of the Y.Doc (it is per-visitor, per the spec). `useSelection` is React state in `App`; nothing about which note is selected is shared across peers.
- **Bring-to-front must not reorder the DOM (drag bug).** `bringToFront` updates the note's `z`, but if the note list is rendered sorted by `z` the dragged node is detached and re-inserted by React (`insertBefore`), which **drops the browser's pointer capture** and ends the drag early (the move is then never applied). The world layer is a transform → stacking context, and every note carries a distinct `zIndex`, so visual stacking is fully determined by `z-index` alone. `BoardViewport` therefore renders notes in a **stable order (by id)** and lets `z-index` do the layering; `bringToFront` then only patches a style attribute and the capture survives. This only reproduces in a real browser — jsdom does not implement pointer-capture loss, which is why the component tests passed and the e2e caught it.
- **Auto-fit re-measures on `editing` change (bug).** `StickyNote`'s fit `useLayoutEffect` depended only on `[note.text]`. Text is committed while the note is still editing (the measuring element is unmounted then), so on a commit — and especially on an Escape-cancel that leaves the text unchanged — the effect never re-ran and a long paragraph stayed at max font. Adding `editing` to the deps re-measures once the static text element remounts (TC-33).
- **Editor is an uncontrolled textarea with a minimal diff.** The textarea keeps its own value; only the delta against the shared `Y.Text` is applied (`applyTextDiff`), so remote updates don't clobber the caret. It clamps to `STICKY_TEXT_MAX_CHARS` (caret restored to the clamped position) and skips composition events (IME guard).
- **Keyboard factorised into `useNoteKeys`.** `Enter`→start edit and `Delete`/`Backspace`→delete + clear selection live in `useBoardDoc`/`useSelection`-agnostic `useNoteKeys(doc, selection)`, used by `App` and the component-test `Harness`, and are no-ops while editing or with no selection (so typing never deletes or commits on Enter).
- **Component-test harness.** `tests/component/harness.tsx` mirrors the `App` wiring and exposes `{doc, selectedId, editingId}` by assigning a props registry during render; drag tests use `vi.useFakeTimers()` + `act(() => vi.advanceTimersByTime(32))` to flush the rAF-coalesced move.
- **`import type { JSX } from 'react'`.** React 19 removed the global `JSX` namespace, so components returning `JSX.Element` import the type from `react`.
- **Story-2 e2e are Chromium-only** for the same missing-`libgtk-3` reason as story 1; all 5 sticky cases pass in Chromium alongside the 8 story-1 cases (13 total).
- **Where the controls are wired.** The design says `ZoomControls`/`NavigationHint` are "wired in `App.tsx`", but `BoardViewport`'s exported contract takes only `children` and owns the camera state. To keep every exported signature exactly as specified, `BoardViewport` renders `ZoomControls` (with the exact prop contract) and `NavigationHint` next to the viewport surface; `App.tsx` mounts the full-window `BoardViewport`.
- **`useCamera` extras.** The hook's documented return was extended with `gestureZoomAtPointer` (needed for Safari `gesturechange`), and `getCamera`/`setCamera` (used by the test-only `window.__vidi6` hook). The documented members are unchanged.
- **Test hook.** `window.__vidi6 = { setCamera, getCamera }` is installed only when `import.meta.env.MODE === 'test'`. E2E runs against `vite build --mode test` served by `wrangler dev`; verified `__vidi6` is absent from the production bundle.
- **wrangler.** Assets-only worker: the `ASSETS` binding had to be removed (`wrangler dev` rejects bindings without a worker `main`; worker code arrives in story 3). `wrangler dev` is started with `--port 27616 --inspector-port 27617` so both its HTTP and inspector ports stay inside the allowed range.
- **Wheel deltaMode.** `LINE`/`PAGE` deltas are converted to pixels with named constants `WHEEL_LINE_PIXELS = 16` and `WHEEL_PAGE_PIXELS = 400` in `BoardViewport.tsx`.
- **Viewport size in jsdom.** jsdom has no `ResizeObserver` or pointer capture; `tests/component/setup.ts` stubs both. `useCamera`'s initial viewport falls back to `window.innerWidth/innerHeight`, so component tests compute expectations from those dimensions.
- **State machine observability.** The viewport element carries `data-interaction="idle|panning"` so TC-13 can assert the Idle→Panning→Idle transitions.
- **Firefox/WebKit e2e are blocked on this machine.** The downloaded Firefox 1555 and WebKit 2370 binaries cannot launch: the host is missing system libraries (e.g. `libgtk-3`) and there is no root to install them (`sudo` is refused). `npm run test:e2e` therefore auto-detects `libgtk-3` and only enables the firefox/webkit projects when it is present; on this machine all 8 e2e cases pass in Chromium (per the session rule that Chromium is sufficient). The chromium/firefox/webkit project definitions are otherwise unchanged and expected to run in a full environment.
- **E2E zoom-limit loops are label-driven** (click until the label reads the limit, with a two-frame settle per click) because reading `isDisabled()` before the rAF-coalesced render raced with the button's disabled state and made Playwright wait forever on an enabled button.
- **Hint tests.** TC-22 tests `NavigationHint` directly (visible → hidden → hidden); the integration behavior (hint present on load, latched away after the first real camera change, kept for the visit) is asserted inside `BoardViewport.test.tsx` (TC-13, TC-29).
- **TC-07 (resize).** Camera maths is a pure value independent of viewport size; the test asserts a zero-delta pan is the identity and the world point at the viewport top-left is unchanged, which is the design's resize invariant.

## Story 3 decisions

- **Integration harness: node pool + wrangler `unstable_dev`.** The spec's "workerd" requirement is met by booting the real Worker (wrangler's local workerd runtime) once per run via `unstable_dev` in `tests/integration/global-setup.ts` and connecting real `ws` sockets; `@cloudflare/vitest-pool-workers` was tried first and abandoned: providers running *inside* workerd need the polyfill path anyway, debugging is far worse, and the pool pins its own vitest major. `WebsocketProvider` gets `disableBc: true` — without it y-websocket's BroadcastChannel syncs clients in-process and a test could pass with the server doing nothing.
- **Sync body wire format.** Every y-protocols sync body is `[kind varuint]` followed by *one* `writeVarUint8Array` length-prefixed blob (state vector / update), not a multi-entry list. `structurallyValidSyncBody` reads exactly one `readBytesChecked` covering the remainder; TC-03 and the unit tests encode the same shape with `writeVarUint8Array`.
- **workerd delivers binary WebSocket frames as `Blob`.** `BoardRoom.toFrame` awaits `data.arrayBuffer()` (also covers ArrayBuffer/Uint8Array) and passes strings through so the shared decoder can reject text frames.
- **`WebSocketPair` in the DO.** The Response returns the *client* half (`new Response(null, { status: 101, webSocket: client })`); `accept()` and all listeners go on the *server* half.
- **yjs `update` event args are `(update, origin, doc, transaction)`** in yjs 13.6 — the second argument is the *origin itself*, not a Transaction. Reading `transaction.origin` silently yields `undefined`, which echoes every update back to its sender (caught by TC-08's no-echo assertion). The relay compares `socket !== origin` and only broadcasts when at least one other socket exists.
- **Relay broadcasts framed updates** (`[MESSAGE_SYNC][writeUpdate]`) — raw Yjs update bytes without the frame prefix would be parsed by peers as a different message type.
- **Awareness is relayed verbatim to every socket including the sender.** Peers never parse it in this story; hearing traffic back is also what keeps idle connections provably alive for TC-29. Query-awareness frames are accepted and ignored (no awareness state is stored until story 6).
- **undici `fetch` reserves the `Upgrade` header** (`invalid upgrade header`), so TC-04/TC-05 use a raw `node:http` request with an `upgrade: websocket` header against the worker entry.
- **Separate tsconfig for worker code** (`tsconfig.worker.json`, `@cloudflare/workers-types` + node types) because DOM and workers-types WebSocket/Request definitions collide in one program. The root typecheck runs both.
- **TC-18 deviation.** A local DO cannot be force-evicted between requests while holding sockets, so "room evicted and re-created" is simulated by closing every socket and having the next visitor's provider rebuild the room through the SyncStep1/SyncStep2 handshake; the observable contract (late joiner gets the full document after full idle) is asserted unchanged.
- **TC-31 uses `ws.terminate()`** (TCP death without a close handshake) to model a dead-but-draining socket, plus a fresh client afterwards to prove the room keeps serving.
- **y-websocket v3.1 API.** `maxBackoffTime` and `disableBc` are top-level constructor options (v2 kept them under `params`); the reconnect-relevant events are `status` (`{status: connecting|connected|disconnected}`), `sync` (boolean) and `connection-close`. `ConnectionState` mapping per contract: first `connected`+`sync(true)` → hidden `connected`; `disconnected` after ever connecting → amber "Reconnecting…"; recovery → green "Connected" (`confirmed`) for `CONNECTED_CONFIRMATION_MS`, timer cancelled if the link drops again mid-confirmation (TC-21).
- **`useBoardDoc(boardId?)` stays callable without an id** so story-2's component harness keeps running local-only (jsdom has no WebSocket); the badge state for a provider-less doc is `connected` (hidden).
- **Routing without a router.** Story 1 shipped no router, so `App.tsx` parses `/b/<boardId>` from `window.location.pathname` directly; `/` (or an id failing `isValidBoardId`) mints `newBoardId()` and `history.replaceState`s to it — story 5 replaces this. `popstate` re-reads the path.
- **Remote text while editing is spliced, not overwritten.** `StickyTextEditor` observes its `Y.Text`; a remote change is located between the local and remote strings' common prefix/suffix and applied to the textarea with the caret shifted by the delta. The uncontrolled textarea's value always equals the last committed ytext (every keystroke commits), so the splice is exact; while an IME composition is in flight the remote text lands in the doc but the textarea is left alone until composition ends (the commit diff may then clobber the remote insert — tests do not cover IME paths).
- **Selection clearing.** `useSelection(doc?)` observes the objects map and nulls `selectedId`/`editingId` when their note disappears; drags end on their own because `moveObject` stops succeeding and the component unmounts.

### E2E decisions (TC-22 to TC-30)

- **Playwright's `context.setOffline(true)` does not drop an already-established WebSocket** (verified on Chromium / Playwright 1.64), so the TC-27 outage cannot be injected at the network layer. Test builds get a `window.__vidi6.simulateOutage(ms)` hook (wired from `BoardConnection.simulateOutage`, which calls `provider.disconnect()` then `provider.connect()` after the outage). The observable product behavior asserted by the PRD — amber Reconnecting badge during the outage, green confirmation and full catch-up after — is asserted unchanged.
- **Participants use isolated browser contexts** (`browser.newContext()`), so each sees a genuinely independent client; readiness = `__vidi6.connectionState === 'connected'`. Snapshots are DOM-level (`sticky-*` left/top/background/text), camera-independent, and convergence is asserted by string equality across all participants.
- **Latency is reported, never hard-asserted** (`[latency]` lines, budget `LIVE_UPDATE_LATENCY_BUDGET_MS`). Model/browsers/server share one machine; a budget assertion would be a flake generator. Observed propagation: 2–18 ms.
- **Nightly soak (TC-29/TC-30)** lives in `*.nightly.spec.ts`, excluded by `testIgnore: /nightly/` in the default config and run via `npm run test:e2e:nightly` (`playwright.nightly.config.ts`, 240 s timeout). TC-30's op grid keeps >100 px gutters between slots so toolbars and drag paths never overlap neighbouring slots, deselects on empty background between cycles, and skips recolours whose swatch is covered (4 s action timeouts prevent Playwright's 30 s default from blowing the wall clock).
- **Pre-existing story-2 e2e flake fixed.** TC-31/TC-32 (zoom drag math) flaked ~7 % even at the story-2 scaffold commit: `useCamera.applyCamera` defers its React state update to the next animation frame, so `__vidi6.getCamera()` (read by `setCamera` polls) could report the new zoom while rendered components still held `zoom = 1`; under parallel load the frame can be delayed arbitrarily. `setCamera` now flushes the batched state synchronously. Relatedly, `StickyNote.endPointer` dropped the last pending move frame, so a released drag could stop short of the pointer; it now commits the pending delta synchronously. 30/30 TC-31/32 repeats and 5× full-suite (100/100) clean.
- **Nightly results on this machine:** 45 s idle holds `connected` on both clients with the first post-idle edit propagating immediately; a 60 s five-editor session ran 120–144 create/move/recolour cycles, every cycle converging within the 1 s budget (mean 5 ms, max 10 ms, 0 over budget) with identical final boards.
