# gufo 0.5.0 decodes 12-18% slower than the build before it, and speculation is why

**Claim tested:** gufo 0.5.0 is no slower than the development build this repository ran before it
(`b722a61`). Its release notes state a timing regression of at most 0.4% by its own checks.

**Status: refuted.** On our own runs 0.5.0 sustains **12 to 18% less decode throughput** at every prompt size,
and the mechanism is visible: it proposes 36% more speculative tokens and accepts a smaller share of them.

Checked 7 October 2026 against every engine request recorded on the Strix Halo box (`conversations.db`,
`requests`; 15,023 requests on 0.5.0 and 12,265 on the old pin, smoke runs excluded).

## Evidence

Same machine, same model (Qwen3.8-Flash-Next), same quantisation (UD-Q4_K_XL), same client, same pack. Decode is
token-weighted: total generated tokens over total decode seconds, so a long request counts for more than a short
one.

Pooled, the gap is 47.0 against 42.2 tok/s. Pooled figures are not worth much on their own, so the comparison is
cut by prompt size, which is the obvious confound:

| tokens in the prompt | old pin `b722a61` | 0.5.0 | change |
|---|---|---|---|
| under 30k | 50.4 | 41.7 | **−17.3%** |
| 30k–60k | 51.2 | 42.1 | **−17.8%** |
| 60k–100k | 49.9 | 42.1 | **−15.6%** |
| 100k and over | 48.4 | 42.7 | **−11.8%** |

**It is slower in every bucket.** A difference in what the runs happened to be doing would not survive that
cut; a difference in the engine does.

## The mechanism

| | old pin | 0.5.0 |
|---|---|---|
| speculative draft acceptance | **79.5%** | **73.4%** |
| draft tokens proposed per request | 444.9 | **607.6** |
| cached prompt tokens per request | 63,159 | 67,720 |
| prompt tokens per request | 66,527 | 68,711 |

0.5.0 proposes **36% more** draft tokens and accepts **6.1 points fewer** of them. Speculative decoding pays for
itself only when drafts are accepted; proposing more and accepting proportionally less is more verification work
per accepted token, which is what a decode-rate drop looks like.

Prompt caching is **not** the cause and in fact improved: 0.5.0 reuses more of each prompt (67,720 of 68,711
cached, 98.6%, against 63,159 of 66,527, 94.9%). Whatever the cache-behaviour changes in 0.5.0 did, they did
not cost this.

## What cuts against it

- **The runs are not matched request for request.** They are different stories with different content. The
  defence is the bucketed cut above: a content difference would not produce a consistent 12–18% deficit across
  four prompt-size bands. It remains an observational comparison, not a controlled A/B.
- **Draft length is adaptive.** Proposing more is not a fault in itself; the engine lengthens drafts when
  acceptance looks good. It is the pairing — more proposed *and* a lower share accepted — that costs.
- **Decode is not the figure this repository ranks on.** Held-out tests passed is. 0.5.0 also closed a tool-call
  defect that ended whole stories (our issue 304), and a story that finishes slowly beats one that dies. On
  quality, the 0.5.0 series is the best gufo result we have: `v2-gufo05-r5` reached 56 of 57 through nine
  stories.
- **The old pin degrades with context and 0.5.0 does not** (50.4 → 48.4 against 41.7 → 42.7). 0.5.0 may have
  traded peak speed for flatness deliberately. Nothing in its notes says so.

## What it changes

- **Nothing about the pin.** 0.5.0 stays: the tool-call fix is worth more than 15% of decode, and it is the
  version the Qwen3.6 fork is built on, so moving would cost that comparison too.
- **It changes what we tell people.** A gufo figure from before 3 October and one from after are not comparable
  on speed, and any throughput comparison that spans the change has to say so.
- **It is worth reporting upstream.** The project's own checks measured ≤0.4%; ours measure 12–18% on 27,000
  requests with a mechanism attached. That is information they do not have.

## How to re-check

```sql
select case when run_id like '%gufo05%' then '0.5.0' else 'old pin' end build,
       case when prompt_tok < 30000 then 'a. <30k'
            when prompt_tok < 60000 then 'b. 30-60k'
            when prompt_tok < 100000 then 'c. 60-100k'
            else 'd. 100k+' end ctx,
       count(*) reqs, sum(generated_tok) tokens,
       round(sum(generated_tok)/sum(generated_tok*1.0/decode_tok_s),1) sustained_tok_s,
       round(100.0*sum(draft_accepted)/nullif(sum(draft_proposed),0),1) accept_pct
from requests
where run_id like '%strix-halo%' and run_id not like '%smoke%'
  and decode_tok_s > 0 and generated_tok > 0 and prompt_tok is not null
group by build, ctx order by ctx, build;
```

Read the buckets, not the pooled figure.
