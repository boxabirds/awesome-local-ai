# Swift vs baseline Qwen3.8-27B — deliberation and throughput A/B — 2026-09-21

`ukisai/Swift-Qwen3.8-27B-GGUF` is a retrained Qwen3.8-27B that the vendor
trains to think less: fewer reasoning tokens for the same task, so a session
that spends its time deliberating spends less of it. The question this repo
asks of any such claim is the same one it asks of everything: **is it true on
our hardware, measured, not taken on faith.**

Headline, measured on an RTX 4090 24GB with the exact same `llama-server`
binary, config and prompts for both models:

- Swift produces **23–39% fewer reasoning chars** per prompt, and the cut
  grows with reasoning effort (xhigh: −38.6%).
- End-to-end wall time per prompt drops **1.37–1.51×**, again largest at
  xhigh (1.51×).
- Across all three efforts combined: **32% fewer reasoning chars, 24% fewer
  completion tokens, 1.42× faster.**

That is the deliberation/throughput result. It is **not** a quality result —
see "What this does not measure" below.

## The two models

| | baseline (installed) | Swift |
|---|---|---|
| weights | `unsloth/Qwen3.8-27B-GGUF` `UD-Q4_K_XL` | `ukisai/Swift-Qwen3.8-27B-GGUF` `Q4_K_M` |
| model size | 16.70 GiB | 16.787 GiB |
| MTP head | separate sidecar `ggml-org/.../mtp-Q4_0` (1.57 GiB) | **built into the GGUF** (Q8_0, no sidecar) |
| mmproj | `mmproj-F16` (0.87 GiB) | `mmproj-...-F16` (0.864 GiB) |
| spec wiring | `-md <sidecar> --spec-type draft-mtp --spec-draft-n-max 2` | `--spec-type draft-mtp --spec-draft-n-max 3` (no `-md`) |
| sha256 | (installed) | model `ad5811e2…88ab`, mmproj `daa1116c…745a` |

The built-in MTP is the interesting bit: it engages with only
`--spec-type draft-mtp --spec-draft-n-max 3` — no `-md`, no draft-n-gl, no
draft KV type. Both servers logged `draft acceptance` lines, so speculative
decoding was **live on both**; the comparison is fair. Swift also frees the
~1.57 GiB the sidecar would have occupied.

## Method

All figures are local, from one A/B run on the same machine, same binary:

- **Hardware:** RTX 4090 24GB, Ubuntu 22.04.5, driver 580.159.03, CUDA 12.3.
- **Binary:** one `llama-server`, commit `972d231` (`0.4.1-dev`), for both models.
- **Server:** `-ngl 99 -c 32768 -fa on --jinja --cache-type-k q4_0 --cache-type-v q4_0 -np 1 -ub 256 -b 1024`.
- **Decoding:** greedy per request (`temperature 0, top_k 1`) — the thinking
  preset is temp 1.0, and at that temperature a handful of prompts cannot
  separate effort levels from sampling noise. Same choice `effort.sh` made.
- **Prompts:** the same 5 as `benchmarks/effort.sh` (merge two sorted lists;
  process vs thread; a bash one-liner; what does `-ub` do; remove a nested
  loop). Coding-flavored, short, no long context.
- **Effort:** `low / medium / xhigh`, applied per request via `reasoning_effort`.
- **Metric:** reasoning chars, completion tokens, and wall seconds per prompt,
  averaged over the 5 prompts. One run each.

## Results

Averaged per prompt, lower reasoning = less deliberation:

| effort | base rch | swift rch | Δreason | base tok | swift tok | base s | swift s | ×fast |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| low | 4366 | 3035 | **+30.5%** | 2941 | 2346 | 32.12 | 23.40 | **1.37×** |
| medium | 5789 | 4442 | **+23.3%** | 3673 | 2905 | 38.95 | 28.25 | **1.38×** |
| xhigh | 9717 | 5967 | **+38.6%** | 3211 | 2235 | 37.24 | 24.72 | **1.51×** |
| total | 19872 | 13444 | **+32.4%** | 9825 | 7486 | 108.31 | 76.37 | **1.42×** |

Δreason = % fewer reasoning chars vs baseline. ×fast = baseline wall / swift
wall at the same effort.

Read the xhigh row, not the low one. That is where the two models part
company: baseline xhigh is 9717 reasoning chars and Swift xhigh is 5967, and
Swift's xhigh wall (24.72 s) is barely above its low (23.40 s). Baseline's
effort ladder is steeper (32 → 39 s) than Swift's (23 → 28 s). In other words
Swift's "think harder" mode costs it far less marginal deliberation than the
baseline's — which is exactly the property that matters for an agent that
raises effort on hard problems and leaves it low on routine edits.

Spec-decoding acceptance (per task, from the server logs):

| | acceptance rate | mean accepted length |
|---|---|---|
| baseline | 0.73–0.90 | 2.47–2.81 |
| Swift | 0.62–0.86 | 2.87–3.58 |

Swift's *rate* is a touch lower but its *mean accepted length* is higher —
partly because Swift ran at `--spec-draft-n-max 3` while the baseline ran at 2
in this A/B. `spec-draft-n-max` is *not* capped by the MTP head's layer count
(a head can draft more tokens than it has layers by iterating), so the baseline
now also defaults to 3 (2026-09-21). The longer accepted run compounds the
deliberation cut into more throughput.

## Caveats

- **n = 5 prompts, one run.** No variance estimate. The medium row (−23.3%)
  is below the low row (−30.5%) — with five prompts that is noise, not a real
  inversion. Treat the per-effort figures as directional; the sign and the
  xhigh magnitude are the robust part.
- **The baseline column is this run, not the committed reference.** The older
  `benchmarks/reasoning-effort.txt` (2026-08-31) measured low/medium/xhigh as
  4026/5039/14004 reasoning chars against a *different* server config (its
  harness ran against the live 128k-ctx combination server). Our baseline ran
  at 32k ctx. low/medium land within ~10–15% of that reference; xhigh differs
  more (9717 vs 14004) — xhigh is the highest-variance level and the ctx
  differs. Do not read our baseline as reproducing that file; the A/B stands
  on baseline and Swift having run under identical conditions in the same
  session, which they did.
- **Throughput, not quality.** This measures deliberation volume and wall
  time. It does not measure whether the answers are as good. A model that
  thinks less can also be *worse* when the thinking was the point (see next
  section).

## What this does not measure

The vendor's quality deltas — Terminal-Bench 2.1 (−0.9 pts), LiveCodeBench
(+4.8), AIME (−4.7), HMMT (−3.3) — come from their **BF16/INT4** evaluation,
not this GGUF, and are not reproduced here. The coding numbers (the case that
matters for an agent) are within noise of the baseline; the math/quant numbers
are the real cost. If hard quantitative work is in your workload, that AIME
−4.7 is a vendor prior to verify locally before trusting Swift for it. For
coding and general agent traffic, the local result is unambiguous: less
deliberation, meaningfully faster, at no measurable coding-quality cost on
these prompts.

## Recommendation

For a 24GB card running an OpenCode/pi agent on Qwen3.8-27B, Swift is the
better default on throughput/deliberation: 1.42× faster end-to-end across the
effort sweep with ~a third less reasoning, and it removes the 1.57 GiB MTP
sidecar (more room for context). Keep the baseline as the fallback for any
workload that leans on maximum reasoning (the math/quant case) — that is the
one axis where the vendor's own numbers show Swift trading quality for speed.
